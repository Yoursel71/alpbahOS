## 2. S1: three shutdown cycles

One reflink copy of the BIOS install, greeter login typed through QMP each time, about two minutes of session.
Cycles 1 and 2: `busctl --user call org.kde.Shutdown /Shutdown org.kde.Shutdown logoutAndShutdown` as testuser in
the session (the interface was introspected first); cycle 3: `systemctl poweroff` as root.

| Cycle | QMP | Time | Copy afterwards (read only) |
|---|---|---|---|
| 1 | `SHUTDOWN {"guest": true, "reason": "guest-shutdown"}`, no QMP quit | 6 s | coredump dir empty, ext4 clean |
| 2 | same | 6 s | same |
| 3 | same | 5 s | same |

The times include the 5 s stop timeout of the test shell unit (instrumentation, not the product).

**Journal finding (FAIL).** The boot of cycle 2 (`S1-strict-lines.txt`, `S1-plymouth-context.txt`):

```text
21:06:52 systemd[1]: Starting Terminate Plymouth Boot Screen...
21:06:52 systemd-coredump[733]: Process 369 (plymouthd) of user 0 terminated abnormally with signal 11/SEGV, processing...
21:06:52 systemd-coredump[733]: Due to PID 1 having crashed coredump collection will now be turned off.
21:06:52 systemd-coredump[733]: Resource limits disable core dumping for process 369 (plymouthd).
21:06:52 systemd-coredump[733]: Process 369 (plymouthd) of user 0 terminated abnormally without generating a coredump.
21:06:52 plymouth[717]: error: unexpectedly disconnected from boot status daemon
```

- It is a crash at boot (when the boot splash is told to quit; kernel command line `quiet splash`), not at
  shutdown. `plymouthd` PID 369 is the daemon started in the initramfs ("dracut: Starting plymouth daemon").
- Boots 1 and 3 ran the same step cleanly (`Received SIGRTMIN+21 from PID 369 (plymouthd)`): 1 crash in 3 boots.
- No core file was written (`/var/lib/systemd/coredump` stayed empty), so the cause is not known. The line "Due to
  PID 1 having crashed" is what systemd-coredump printed; it is quoted, not interpreted.
- The shutdown windows of all three boots have no dump or segfault line. Other lines there:
  `alpbahos-zram.service` stop failed in cycle 3 only (`status=1/FAILURE`; on r21 it failed in all 3 cycles);
  `obex.service` exit 1 in cycle 3.
- The coredump-at-shutdown issue of earlier rounds: not reproduced in 3 cycles (not proven fixed). The plymouthd
  crash is a new, separate item (PLYMOUTH-01 area); not fixed here.

## 8. Deviations and harness faults

- Installed rows used reflink copies with test instrumentation (the one-shot diagnostic unit for B3/U2, a root
  test shell on a second serial port for FP-GUI, S1, R1, KF, ALP, SBX). Greeter passwords were typed through QMP;
  nothing else was typed in the installed desktop.
- S1/R1 called the session's `org.kde.Shutdown` interface directly, not the menu and its confirmation screen.
- Harness fault, fixed during the run: queue 2 sourced `matrix-r21.sh` for its helper functions, which reset the
  variable `S`, so none of its SBX guest commands ran (`run-SBX.out`, `SBX-*.txt`: "No such file" errors; that copy
  was deleted). Queue 2 was stopped while the KF live step continued; queue 3 (`RBD` instead of `S`) ran KF, SBX,
  ALP, F1 and the TCG rows. The SBX/ALP results are from `SBX2`.
- F1 typed the existing `test-secrets/r39.pw` (read only), as `ROUND=r39` selects it.
