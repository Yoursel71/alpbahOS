# M04 LFS 12.4-systemd Chapter 8 package coverage — 24 September 2026

## Scope and result

This matrix compares the official LFS 12.4-systemd Chapter 8 package list with
the staged manifests currently committed under
`manifests/lfs-base/`. The official chapter contains 79 package entries.
There are 25 staged package manifests, covering 8,433 recorded paths. These
are controlled `DESTDIR` install trees, not historical records of how the
current `/mnt/lfs` rootfs was installed. A separate read-only Builder source
cache audit found all 57 packages that were missing manifests at the time had
a candidate source archive at `/mnt/lfs/sources/` root; three have since had
source hashes verified for stage capture, leaving 54 without manifests.
Archive presence is not checksum or build evidence; each package source still
must be checked before use. The live
`/mnt/lfs/var/lib/alp/db.json` still has an empty `packages` object.
Accordingly, no row below is marked as an installed ownership record.

“Rootfs comparison” is a read-only comparison of a staged manifest to the
current rootfs. A full match only establishes that the compared manifest paths
match at the time of comparison; it does not independently prove that package
was the historical installer. Coreutils' special Chapter 6 bootstrap
comparison is not a final-system comparison.

## Interpretation and next actions

- Manifest coverage is 25/79 Chapter 8 entries. The other 54 packages need a
  proven record or a controlled install capture before the chapter inventory
  is complete.
- Twenty-three ordinary per-package `.log` preflight reports exist; 21 show
  mismatches and Lz4 and Man-pages are the only ordinary reports with a full
  exact match. Iana-Etc matches both package files; the shared `/etc`
  directory's uid differs.
  Coreutils has a separate Chapter 6/bootstrap comparison JSON, not a final
  rootfs preflight. Zlib's 14/14 claim is recorded in the assessment and
  WORKLOG, but a separate report file was not preserved.
- Neither stage success nor exact content comparison alone proves historical
  package ownership. Each package still needs its source identity and path
  record reconciled to the installed base; shared paths need explicit
  ownership rules.
- Do not merge mismatching stage trees or infer package ownership from Unix
  uid/gid. M04 remains open until the complete base is represented and the
  installed rootfs's ownership data is safely verifiable.
