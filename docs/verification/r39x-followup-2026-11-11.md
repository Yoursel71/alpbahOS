## 1. PLY-CRASH-01: plymouthd SIGSEGV when the boot splash is hidden

### Method

On a reflink copy of the BIOS install (test instrumentation, copy only):

- `r39y-plycore.service`, ordered before `plymouth-quit.service`: `prlimit --core=unlimited` on the `plymouthd`
  that was started in the initramfs. Its core limit was 0, which is why the r39x journal said "Resource limits
  disable core dumping".
- `/etc/sysctl.d/99-r39y-core.conf`: `kernel.core_pattern=/var/tmp/core.%e.%p.%t`. systemd-coredump treats a
  process left over from the initramfs (it lives in `init.scope`) as PID 1 and turns collection off, so cores go to
  a plain file instead.
- `plymouth.debug` added to the copy's kernel line.
- The r21m test shell, used for the per-boot check and the power-off.

Then 20 boot cycles, each a fresh QEMU: KVM, BIOS, virtio, 4 GiB, intel-hda, the same as S1 in r39x.

### Result: 3 crashes in 20 boots (cycles 5, 9, 11), 3 core files

`run-PLY.out` lists every cycle; `PLY-cores/` holds the three cores (mode 600). gdb on the host, with the copy as
sysroot, gave the same stack for all three (`PLY-core-analysis.txt`). The binaries are not stripped, but gdb found
no line tables, so the frames are function names from the dynamic symbols:

```text
#0  ply_list_get_first_node ()          libply.so.5      (2 cores: mov (%rdi),%rax with a NULL list)
    ply_list_node_get_data ()           libply.so.5      (1 core: freed list node)
#1  ply_keyboard_remove_input_handler () libply-splash-core.so.5
#2  stop_script_animation ()            plymouth/script.so     (theme alpbahos, script plugin)
#3  hide_splash_screen ()               plymouth/script.so
#4  ply_boot_splash_hide ()             libply-splash-core.so.5
#5  on_boot_splash_idle ()              plymouthd
#6  ply_event_loop_process_pending_events () / #7 ply_event_loop_run () / #8 main ()
```

- Process: `/usr/sbin/plymouthd --attach-to-session --pid-file /run/plymouth/pid`, started in the initramfs. Its
  files show as "(deleted)" in the core because the initramfs is gone after the switch to the real root; gdb used
  the root file system's copies of the same build.
- Renderer: `renderers/drm.so`. `UseSimpledrm=1`, so plymouth starts on simpledrm and then gets virtio_gpu.
- Plymouth package: alp record version 26.134.222.

### Timing (journal of the copy, `PLY-timing.txt`)

In all three crash boots, `Starting Terminate Plymouth Boot Screen` (plymouth-quit) comes 11 to 38 ms after the
kernel registered the virtio_gpu framebuffer that replaces simpledrm:

| Boot | virtio_gpu fb0 | plymouth-quit starts | Gap | Result |
|---|---|---|---|---|
| 20ce091f (crash) | 3.621 s | 3.632 s | 11 ms | crash |
| 7b3baaab (crash) | 3.644 s | 3.681 s | 37 ms | crash |
| 9ffe57ea (crash) | 4.129 s | 4.167 s | 38 ms | crash |
| 8323a703 | 4.704 s | 4.779 s | 75 ms | SIGRTMIN+21 at 4.905 s, finished |
| 47baf81b | 3.368 s | 3.462 s | 94 ms | finished |
| 56f4b46f | 3.962 s | 3.974 s | 12 ms | finished |

In every crash boot, the effects were the same:

- `plymouth-quit.service: start operation timed out` after 20 s, then "Failed to start Terminate Plymouth Boot
  Screen".
- SDDM started about 20 s late.
- The next power-off did not finish within 60 s, so the harness ended the guest with a QMP quit.

### Proposed cause (not fixed, not proven at line level)

When the splash is hidden, the script plugin removes its keyboard input handler from a keyboard object that has
already been freed or has an empty handler list. The crash comes only when plymouth-quit arrives while plymouth is
still handling the simpledrm to virtio_gpu device switch. The likely race: the device manager frees the
simpledrm-era seat or keyboard while `script.so` still holds `plugin->keyboard`. One clean boot also had a short gap
(12 ms), so the gap alone does not decide it.

Candidates to try, in a new round:

1. `UseSimpledrm=0` in `plymouthd.conf`. Plymouth then waits for the real DRM device, so there is no handover.
   This is the cheapest test.
2. Compare the plymouth source of 26.134.222 (`src/plugins/splash/script/plugin.c`, `stop_script_animation`, and
   the `set_keyboard`/`unset_keyboard` paths) with upstream fixes for keyboard use-after-free during device
   removal. Then patch the recipe if a fix exists.
3. Rebuild with `-g` line tables, so a core gives file and line.

The old shutdown-coredump item is a different place: this crash happens at boot.

## 2. L4: TCG BIOS boot hang

The r39x hang (run 1) had stopped right after SMP bring-up with `RIP=ffffffffa150d307` under KASLR. Here the r39
live ISO's own kernel and `initramfs-live.img` were booted by QEMU direct kernel boot (BIOS pc machine, TCG,
`-cpu qemu64`, 6 GiB). The ISO's GRUB arguments were used plus `nokaslr`, which shows on the kernel command line in
every serial log. The installed and ISO `vmlinuz` have the same sha256 (`2e066173...`), so the installed image's
`System.map-7.1.8-alpbahos` was ready for symbols (`L4k/System.map`).

| Runs | vCPUs | Result | Host load |
|---|---|---|---|
| L4n-1..5 | 4 | 5 of 5 reached the serial login prompt (about 40 s) | 2.7 to 3.5 |
| L4c-1..2 | 1 | 2 of 2 reached the login prompt (about 70 s) | 2.4 to 2.6 |

No hang in 7 runs, so there was no RIP to map. The r39x hang happened at host load 4 to 10, while the other
session was building; that load was not reproduced here. The r39x RIP cannot be mapped without its KASLR offset.
Still open: it is not known whether the hang is load-dependent TCG timer behaviour or a kernel bug. A later TCG run
on a loaded host, with `nokaslr` and this script, would give the symbol.

## 4. PLY-FIX-01 (2026-11-12): UseSimpledrm=0, and the cause in the source

### Test

Script `scripts/rebuild/r39y/ply-fix-r39y.sh`; evidence `r39y/PLYFIX/`, log `r39y/run-PLYFIX.out`.

Setup:

- A fresh reflink copy of the kept r39 BIOS install, with the same core setup as section 1.
- Setup boot, settings unchanged: screenshots once a second.
- In the guest: `/etc/plymouth/plymouthd.conf` `UseSimpledrm=1` → `0`.
- `/usr/share/plymouth/plymouthd.defaults` was left at 1. dracut takes the module list only from that file; with
  0 there, every GPU driver would go into the initramfs (`scripts/rebuild/r23/plymouth-r23.sh` lines 42-52).
- The initramfs was rebuilt with `scripts/rebuild/iso/live/target-initramfs.sh` (rc 0, 57,711,554 → 57,711,695
  bytes, 2 DRM modules as before). `lsinitrd -f etc/plymouth/plymouthd.conf` reads `UseSimpledrm=0`.

Then 20 boots (KVM, BIOS, virtio, 4 GiB, intel-hda).

| | Before (r39, `UseSimpledrm=1`) | After (`UseSimpledrm=0`) |
|---|---|---|
| plymouthd crashes (core files) | 3 / 20 (section 1) | **0 / 20** |
| plymouth-quit result | timeout in the crash boots | success in 20 of 20 |
| Splash on screen (screenshots once a second from QEMU start) | logo, bar and "Başlatılıyor" from about 7 s to 11 s (`FIX-setup/boot-08s.png`) | **not seen**: the GRUB frame stays until about 10-12 s, then black, then the greeter (`FIX-c01/boot-10s.png`, FIX-c02 the same) |
| "Show Plymouth Boot Screen" / virtio_gpu / plymouth-quit start (kernel time) | 3.4 / 3.6 / 3.6 s (section 1) | about 3.2-4.8 / 3.4-5.1 / 3.4-5.1 s (`run-PLYFIX.out`): plymouth can draw only after virtio_gpu arrives, and quit follows 0.05-0.4 s later |

So `UseSimpledrm=0` removes the crash in this test, but the splash disappears: GPU drivers are modules outside the
initramfs (D150), so there is nothing to draw on until after the switch to the real root.

### Cause in the source (plymouth 26.134.222, `scratch-lfs-bench/r10/dl/plymouth-26.134.222.tar.xz`)

`src/libply-splash-core/ply-device-manager.c`:

- `free_keyboards_for_renderer()` (line 153) frees the keyboards of a renderer that goes away with
  `ply_keyboard_free (keyboard)` (line 169), but does not call `manager->keyboard_removed_handler`. That handler is
  stored (lines 83 and 1288) and is never called anywhere in the file.
- The display path does call its handler: `free_displays_for_renderer()`, line 142.
- The simpledrm renderer is freed exactly when the real DRM device arrives: `free_simpledrm_renderer` →
  `free_devices_from_device_path` → `free_keyboards_for_renderer`, called from
  `create_devices_for_terminal_and_renderer_type`.

Therefore `main.c` `on_keyboard_removed()` → `ply_boot_splash_unset_keyboard()` does not run. The script plugin
keeps `plugin->keyboard`; its `unset_keyboard` would clear it (`src/plugins/splash/script/plugin.c` lines 456-459).
`stop_script_animation()` (lines 396-400) then removes its input handler from the freed keyboard. That matches all
three cores.

Proposed patch (not built, not tested; applies with `patch -Np1 --dry-run`): call the handler before the free.
Patch file: `docs/handoffs/ai/patches/037-plymouth-keyboard-removed.patch`. Handoff with the build steps:
[037-plymouth-simpledrm-2026-11-12.md](../handoffs/ai/037-plymouth-simpledrm-2026-11-12.md). Upstream main
could not be compared: gitlab.freedesktop.org refused the automated fetch (bot protection).

## 5. PLY-FIX-02 (2026-11-12): patched plymouth, UseSimpledrm=1

Script: `scripts/rebuild/r39y/ply-fix2-r39y.sh`. Evidence: `r39y/PLYFIX2/`, log `r39y/run-PLYFIX2.out`, check
`PLYFIX2/FIX2-verify.txt`.

### Build

- **Where:** inside a booted reflink copy of the kept r39 BIOS install. It has gcc, meson, ninja, patch and all
  the `.pc` files plymouth needs. r4-root and the ISO build were not touched.
- **Inputs:**
  - source `r10/dl/plymouth-26.134.222.tar.xz`, sha256 `6ee10682…bb0`, the same as `packages.tsv` row 402;
  - patch `docs/handoffs/ai/patches/037-plymouth-keyboard-removed.patch`, sha256 `d5f81507…7be9`.
- **Options:** taken from the original build log (`r10/plymouth/build.log`, `build-pkg-r10.sh` meson branch):
  `--prefix=/usr --buildtype=release -Db_lto=false -Dbackground-color=0x0b1014 -Dbackground-end-color-stop=0x0b1014
  -Dbackground-start-color-stop=0x0b1014 -Ddocs=false -Dgtk=disabled -Drelease-file=/etc/os-release
  -Dsystemd-integration=true -Dtracing=false -Dudev=enabled -Dupstart-monitoring=false`. Same build directory
  (`/tmp/plymouth-26.134.222`), cleared environment.
- **Control build without the patch:** same size as the installed library (182,824 bytes) but not byte-identical
  (`dc8d569b…` vs `da30f747…`). The guest is not the original chroot, so the result is a close rebuild, not a
  reproducible one. The exported symbols of the patched and original libraries are the same.
- **What changed on the copy:**
  - only `/usr/lib/libply-splash-core.so.5.0.0` was replaced (patched `fa3b99cf…`; original saved in the copy);
  - `plymouthd` unchanged;
  - `UseSimpledrm=1` unchanged.
- **Initramfs:** rebuilt with `target-initramfs.sh` (rc 0, 57,711,785 bytes). Its `libply-splash-core.so.5.0.0`
  (`04490118…`, 180,936 bytes) is byte-identical to `strip -g` of the patched build (dracut strips debug info), and
  differs from `strip -g` of the original. So the plymouthd that starts in the initramfs uses the patched code.

### Test

30 boots, each a fresh QEMU (KVM, BIOS, virtio, 4 GiB, intel-hda), host load about 2, same core setup as
sections 1 and 4.

| | r39 as shipped (section 1) | Patched plymouth, `UseSimpledrm=1` |
|---|---|---|
| plymouthd crashes (core files) | 3 / 20 | **0 / 30** |
| plymouth-quit | timed out (20 s) in the crash boots | success 30 / 30 |
| Boots where plymouth-quit started 0-40 ms after virtio_gpu registered fb0 (where all 3 r39 crashes fell) | 3 crashing | 9 (gaps 3, 6, 12, 12, 18, 25, 30, 31, 36 ms), none crashing |
| SDDM start (kernel time) | about 23.7-24.3 s in the crash boots | 3.9-5.3 s in every boot |
| Power-off after the cycle | did not finish within 60 s in the crash boots | 30 / 30 within 60 s |
| Splash | logo and bar about 7-11 s | **present**: logo, "Başlatılıyor" and the bar at 7-10 s (`FIX2-c01/boot-08s.png`; `FIX2-c02/boot-09s.png` with the bar further along); the same frame sizes as the unpatched build boot `FIX2-build/boot-08s.png` |

Chance check: if the patch changed nothing, with the r39 rate (3/20), 0 crashes in 30 boots would happen about
0.8% of the time. The 9 boots inside the crash window make the result stronger than the plain count.

### Limits

- QEMU only (virtio_gpu); not tested on real GPUs (i915, amdgpu, nouveau).
- Not tested with the LUKS prompt (keyboard input during the device switch).
- Upstream main was not compared (bot protection on gitlab.freedesktop.org).
- The fix still has to be built into the plymouth record and an ISO (handoff 037).
