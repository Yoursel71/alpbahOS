## 1. What was confirmed in the old code (the finding)

Read in `alp.py` at `dc78ce9`:

- `main()` called `load_index()`, which only parsed JSON. No signature existed anywhere; `cmd_update()` took any
  https or local source and `_update_git_catalog()` fast-forwarded to whatever upstream had. The comment above
  `cmd_update` said so ("the catalog itself is not signed").
- `install_recipe()` and `upgrade_recipe()` ran each step with
  `subprocess.run(step, cwd=src_dir, check=True, ...)`: as the caller (root for a system install), with the
  caller's whole environment, with network.
- Recipes were read from disk with no hash; only the source archive had a sha256, and that value came from the
  unsigned recipe.
- `_merge_staged()` copied modes with `shutil.copymode`, so a setuid file in a DESTDIR became a setuid file in
  the root, owned by root when alp ran as root. Device nodes, sockets and FIFOs were already refused
  (`_walk_staged`).
- Found while implementing, not in the review: a catalog bundle was installed by copying **every** file in the
  archive next to the catalog. With a signed index that would still have let the sender add files of their own
  (for example a keyring, if keys live in the catalog directory). And `alp_search()` in the PackageKit wrapper
  treated exit code 1 as "no hits", so a refused catalog would have looked like an empty result.

## 6. Deviations from the brief and from the note

- `valid_until`: 90 days and warning at local use (D172), as the brief decided; the note is updated.
- `alp.py` is one commit, not several. Signature, sandbox and stage code share the `Paths` fields and `main()`;
  intermediate versions were not built and tested, so they are not offered as commits.
- Normalising drops group/other write everywhere, not only under `/usr` (section 8, finding 2).
- The stage checks are a new function `_preflight_stage()` called just before `_preflight_merge()`, not code
  inside `_preflight_merge()` (whose signature has no access to the staged files).
- Extra to the brief: `/run` private in the sandbox; `--unshare-uts`; `--jobs`; `recover` needs no catalog;
  bundles install only pinned files; git update refused when the keyring is inside the checkout; `alp update`
  with an unusable local catalog needs `--source`; a present-but-bad signature is refused even with
  `--allow-unsigned`; `alp_search` raises on an alp error.
- The root-only rule for `--allow-unsigned` and `--no-sandbox` is enforced in `main()`. The engine takes a
  `TrustPolicy` / `Paths.sandbox`; the older engine-level tests set them directly as an ordinary user.
- The build environment is cleared also with `--no-sandbox` (`CC`, `CFLAGS`, `MAKEFLAGS` from the caller are not
  passed). Build scripts that relied on exported variables must put them into the recipe.
- Other points are listed in note section 9.

## 7. Known limits and open security questions

Stated as limits, not as "safe":

- A malicious recipe that we signed is not covered (note section 2). The sandbox limits the build; what the
  package installs runs later with whatever rights it has.
- Trust in the catalog object (narrowed by section 8, finding 1): entries of a signed catalog are `SignedEntry`
  objects and `read_recipe()` refuses one without `recipe_sha256`. What is left: a caller that hands the engine a
  plain dict it built itself gets no digest check when the dict has no digest. Only `main()` and the tests
  construct catalogs.
- A bundle is unpacked (`safe_extract`, into the work directory) and a git remote is fetched **before**
  verification. A huge archive can fill the disk; git parses untrusted objects.
- The sandbox leaves `/` readable: the build user can read whatever any unprivileged local user can. Path-based
  unix sockets outside `/run` and `/tmp` stay reachable. No seccomp filter, no cgroup limits (CPU, memory, disk
  in the stage and the build log are unbounded).
- "No build-user process survives a step" rests on the pid namespace being torn down
  (`test_a_process_left_behind_by_a_step_does_not_survive_it`); a process running as `alpbuild` started some
  other way could change the stage between the check and the merge. With `--no-sandbox` there is no such
  protection at all.
- Ownership checks on trust files look at the file, not at its parent directories.
- The rollback floor is only as good as the database: on a fresh system nothing is stored until the first
  install, upgrade or update (the update floor also uses the verified local catalog).
- Symlink escape is decided lexically (note section 9); absolute targets are accepted for ordinary packages.
- `signed_keyring_version` only prints a hint.
- gpgv is given the keyring and signature as `/dev/fd/N` (memfd). Tested with GnuPG 2.4.9 only; the image has
  GnuPG 2.5 per the note. **Not tested there.**
- uid 65534 was used for the root tests; the real `alpbuild` user path (`pwd.getpwnam`) was tested only for the
  "user missing" refusal.
