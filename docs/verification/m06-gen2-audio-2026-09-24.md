## PipeWire attempt — failed roundtrip

Same SSH user session, after starting D-Bus, PipeWire, WirePlumber and
`pipewire-pulse.socket` and allowing five seconds for device discovery:

- `wpctl status` showed PipeWire 1.4.7, WirePlumber 0.5.10, ALSA Loopback
  device 41, default sink 45 and source 46.
- `wpctl inspect 45` identified sink 45 as ALSA card 0/device 0 playback;
  `wpctl inspect 46` identified source 46 as ALSA card 0/device 0 capture.
- `pw-play -v --target=45 /tmp/m06-440hz-sine.wav` streamed and drained; exit 0.
- Concurrent `arecord -D hw:Loopback,1,0 -f S32_LE -c 2 -r 48000 -d 3
  /tmp/m06-pw-direct-capture.wav` produced 144000 frames, but peak=0 and RMS=0,
  then returned `Input/output error` (exit 1). The target PCM did not contain
  the played signal. A prior attempt with S16_LE was rejected because this
  capture endpoint only advertised S32_LE.
- `speaker-test -D pulse` returned `Unknown PCM pulse`; the ALSA Pulse plugin
  is not available in this image.
- A second attempt generated a 12-second 440 Hz stereo S32_LE WAV in the guest
  temp directory and started `arecord` one second before `pw-play`. Playback
  was `RUNNING` on `/proc/asound/Loopback/pcm0p/sub0/status` with S32_LE,
  48 kHz stereo params; `wpctl status`/`pw-link -l` showed both `pw-play`
  channels actively linked to sink 45 playback ports. Despite that, capture
  returned 480000 frames of silence (peak=0, RMS=0, SHA-256
  `23b4d84bf28117ac994c71da107a4c4912f262155aeec2a7c3d0909549061b58`) and
  ended with `File descriptor in bad state` (exit 1). `pw-play` completed
  normally (exit 0). This confirms sink graph activity but not PCM delivery to
  the loopback capture endpoint; the routing failure's cause remains open.
- In a final concurrent observation with capture started before playback,
  `/proc/asound/Loopback/pcm0p/sub0/status` showed playback `RUNNING` with
  `appl_ptr`/`hw_ptr` advancing, while the paired
  `/proc/asound/Loopback/pcm1c/sub0/status` and `hw_params` were already
  `closed`; `arecord` had returned the same `File descriptor in bad state`
  failure. This narrows the symptom to the ALSA capture substream closing
  while PipeWire playback remains active; it does not establish why the
  kernel/ALSA capture endpoint closed.

Therefore PipeWire device discovery and playback stream startup are observed,
but PipeWire-to-ALSA end-to-end capture is not verified and must remain a
failure/open item. No package was installed in the guest. The VM's test-only
audio setup does not establish physical audio support.

## Same-session retest — 24 September 2026

The Audio VM was still running at `172.28.174.20` (MAC
`00-15-5D-00-02-0B`). A fresh SSH connection showed both `Loopback` PCM
devices, `/dev/snd` group/mode, and the `sa` audio membership. Initially the
user PipeWire services were inactive. Starting the services in one SSH call
made them visible to `wpctl`; after that SSH process exited, the user manager
closed D-Bus and stopped PipeWire/WirePlumber. This is consistent with the
session-scoped user manager and means service startup and audio probes must run
inside the same SSH session.

The test was repeated with service startup and probes inside one SSH session:

- `systemctl --user start dbus.socket pipewire.service wireplumber.service
  pipewire-pulse.socket` succeeded. `wpctl status` showed PipeWire 1.4.7,
  WirePlumber 0.5.10, sink 45 and source 46.
- A generated five-second 48 kHz stereo S32_LE sine WAV was played to sink 45.
  `pw-play` exited 0. During playback,
  `/proc/asound/Loopback/pcm0p/sub0/status` showed `RUNNING` and advancing
  pointers.
- `arecord -D hw:Loopback,1,0 -f S32_LE -c 2 -r 48000 -d 7` exited 1; during
  playback the paired `/proc/asound/Loopback/pcm1c/sub0/status` was `closed`.
  No PCM level/hash was accepted from this run because the guest-side stats
  process was killed before it produced a measurement.
- The inverse experiment (`aplay` to ALSA device 1 while `pw-record --target=46`
  was active) did not complete a record file; it is inconclusive. It is not
  counted as a pass or a second failure mode.

The session-lifecycle issue explains earlier `pw_context_connect(): Host is
down` probes made after service startup and test were split across SSH
connections. Keeping startup and testing in one connection removed that
transport symptom but did not fix the ALSA paired-capture closure. Temporary
files created by this retest were removed. No guest package, persistent
configuration, image, or rootfs content was changed.

## Inverse ALSA-to-PipeWire probe — 24 September 2026

The test was repeated in one SSH session after starting the session D-Bus,
PipeWire, WirePlumber, and `pipewire-pulse.socket`. `speaker-test` to
`hw:Loopback,1,0` passed with S32_LE, 48 kHz stereo, and exit 0; S16_LE was
rejected by this PCM as an unsupported playback format. `wpctl status` showed
the expected sink 45/source 46. However, `pw-record --target=46` was not
bounded by the attempted SIGINT cleanup: its WAV grew to 990,941,184 bytes
(946 MiB) during the short probe, while `speaker-test` was active. The recorder
returned exit 1, and no signal-level analysis was performed; this is not a
roundtrip pass or evidence that PipeWire captured the sine. The exact temporary
WAV and logs created by this probe were removed immediately; guest `/tmp`
returned to 11 MiB used / 946 MiB available. No packages, persistent settings,
image, or rootfs files changed. Any later inverse-direction capture must impose
a hard output-size limit before writing guest data.

### Bounded raw recapture

A follow-up kept `speaker-test` playing S32_LE, 48 kHz stereo sine to
`hw:Loopback,1,0` and piped `pw-record --raw --target=46` through `head -c
1048576`. Playback exited 0 and the recorder pipe closed at exactly 1,048,576
bytes (the recorder's 141 status is the expected SIGPIPE after the cap). The
raw capture was copied to the Windows host and analyzed there: 131,072 stereo
frames, left-channel peak 0, RMS 0, 0 nonzero samples; SHA-256
`30e14955ebf1352266dc2ff8067e68104607e750abb9d3b36582b8af909fcb58`. This is
measured silence at PipeWire source 46 during active ALSA playback, not a
roundtrip pass. The guest raw file, playback/recorder logs, and local analysis
copy were removed; guest `/tmp` returned to 11 MiB used / 946 MiB available.
No package, persistent setting, image, or rootfs content changed.

While both streams were live, `pw-link -l` showed source 46's capture_FL/FR
ports linked to `pw-record` input_FL/FR, and `pw-record -v` reached `streaming`
with target 46. At the same moment, `/proc/asound/Loopback/pcm1p/sub0/status`
was `RUNNING` for the ALSA playback, but the paired
`/proc/asound/Loopback/pcm0c/sub0/status` remained `closed`; the other inspected
substream-0 playback/capture endpoints (`pcm0p`, `pcm1c`) were also closed. This rules out a missing PipeWire
graph link as the cause of the measured silence. It places the unresolved gap
at or before PipeWire's ALSA capture backend opening the Loopback device.

The same guest's user journal records the concrete backend error:
`spa.alsa: front:0c: snd_pcm_start: Input/output error`, followed by
`alsa_input.platform-snd_aloop.0.analog-stereo` transitioning
`suspended -> error (Start error: Input/output error)`. The failure therefore
occurs as PipeWire starts the ALSA capture PCM, after the graph link is made;
the underlying reason for the kernel ALSA start error remains unresolved.

### Direct ALSA `front:0` control

To distinguish a generally broken ALSA alias from PipeWire's use of it, the
same playback signal was sent to `hw:Loopback,1,0` while `arecord -D front:0`
captured S32_LE, 48 kHz stereo for three seconds. `arecord` exited 0 and wrote
144,000 frames (guest WAV 1,152,044 bytes, SHA-256
`900e149785386e38a9d319a6956b952f037d88a761e3366418dc487263b03faa`). Host
analysis measured left-channel peak 110,966,738, RMS 78,458,011.18, all 144,000
samples nonzero, and 440 Hz projection peak 104,974,714.92. Thus ALSA's
`front:0` alias captures the paired signal when driven directly; the remaining
failure is specific to PipeWire's SPA ALSA source start/negotiation path. The
exact WAV and test logs were removed from the guest and the local analysis copy
was removed. Pre-existing unrelated `/tmp/m06-*` files were left untouched.

As a format-acceptance control, direct `arecord -D front:0` was then repeated
while matching `speaker-test` playback ran at 48 kHz stereo, first S16_LE and
then S32_LE. Both captures exited 0; the one-second WAV sizes were 192,044 and
384,044 bytes respectively. The temporary files were removed. This shows the
ALSA alias accepts both sample formats in this paired loopback test; those two
short control files were not separately analyzed for signal level.

### Matching S16 PipeWire retry

PipeWire's source ID was re-read from `wpctl status` and verified with
`wpctl inspect` as `Audio/Source`, `api.alsa.pcm.stream=capture`,
`api.alsa.path=front:0` (ID 46 in this session). With S16_LE/48 kHz playback
running on `hw:Loopback,1,0`, `pw-record --target=46 --format=s16` reached
`streaming` and was capped at 1,048,576 raw bytes. It returned 141 because
`head` closed the pipe at the cap. The capture SHA-256 was again
`30e14955ebf1352266dc2ff8067e68104607e750abb9d3b36582b8af909fcb58`, identical
to the previously analyzed all-zero buffer. A live follow-up showed the
source-to-recorder ports linked while S16 playback `pcm1p/sub0` was `RUNNING`
and capture `pcm0c/sub0` was `closed`. Matching the source's 16-bit resolution
to playback therefore did not restore PCM capture. Guest scratch files were
removed and `/tmp` returned to 11 MiB used / 946 MiB available.
